# 消息首页（DB 驱动）设计

## 一句话

把「主动查消息」从**打开微信窗口 OCR** 改成**读本地解密数据库**，并在首屏把
「关键信息 + 关键操作 + 对话」放在一起；用户不必再回到原生对话框。

## 为什么换数据源

| | OCR 方案（旧） | DB 方案（新） |
|---|---|---|
| 读取方式 | 截图 → 逐帧识别 → 点击切换会话 | 读 `plain/session/session.db`、`plain/message/message_N.db` |
| 是否占用微信 | 是（切前台、抢走用户正在看的会话、清未读） | 否（只读副本，`mode=ro&immutable=1`） |
| 覆盖范围 | 只有左侧当前可见的十来行 | 全部会话、全部历史 |
| 准确度 | 依赖识别率，长名字被省略号截断就废 | 原生字段，无识别误差 |
| 速度 | 单会话列表区 OCR ≈ 0.8–1.5s（RapidOCR ~98% 耗时） | 一次 SQL 遍历，毫秒级 |
| 失败模式 | `conversation_unverified` / `layout_unverified` / `wechat_in_use` | 数据库没解锁（拿不到密钥） |

`wechat-db-lab` 已经负责「取密钥 → 解密副本 → 明文目录」，message-agent 只读那份
明文。watcher 子进程常驻，因此 DB 读取是**随取随用**的，没有额外解锁成本。

## 信息架构

```
消息（首页，默认）      关键信息 + 关键操作 + 对话
待办                    要做 / 在做 / 做完（复用现有 todos）
自动回复                规则、状态、处理记录
回复配置                说话方式、产品与政策
设置                    模型、开发者模式（含原生对话框入口）
```

原「消息整理」页在首版被整体撤掉，因为它骑在 OCR 上。现在它回到首页，但只保留
一条路径：**点一下「整理消息」→ 读 DB → 出结论 + 待办**，不再有自由输入框、不再有
「只刷新会话列表」、「重新整理 / 清空」这些围着 OCR 打转的补丁。

## 首屏三块

### 1. 关键信息（`GET /api/home`，纯确定性，不调模型、不碰微信）

全部由 DB + 本地状态直接算出来，所以首屏是**瞬间**出现的：

| 卡片 | 来源 | 口径 |
|---|---|---|
| 最近有动静 | `SessionTable` 按 `sort_timestamp` 倒序 | 去掉系统会话、`is_hidden=1` |
| 等你回复 | 每个会话最近一条**收到的**消息晚于我最后一条发出 | 这是「需要回复的人」的确定性定义 |
| 待办 | `crm.counts()` | 未完成（要做 + 在做） |
| 自动回复异常 | `projectInbox` 的 `bucket === 'error'` | 读不到微信 / 上次没完成 |

「等你回复」刻意**不**用模型判断：判断标准只有一个 —— 最后一条是对方发的。模型只在
「整理」那一步负责理解内容，不负责决定谁在等我。

### 2. 关键操作

- **整理消息**（主操作，一次点击）：读最近若干个会话的正文，交给模型归纳出
  「发生了什么 / 谁需要你回应 / 有哪些事要做」，结果留在页面上，待办可勾选后入库。
- 点任意联系人或群 → 进入会话视图（DB 正文 + 待办 + 跟进 + 该会话的对话）。

### 3. 对话

一个和「消息助手」的对话区，和普通的通用 Agent 不是一回事：

- 复用 `message-agent` 预设（persona 已经限定在消息域，没有编程/联网工具）。
- 每次提问由 Host 注入**一份 DB 快照**（最近会话 + 最近正文），答案直接建立在真实
  消息上，而不是靠模型去调 OCR 工具。
- 同时给这个会话注册一个 DB 工具 `read_wechat_messages`，需要更深的历史时模型可以
  按名字读取 —— 走的还是数据库，不开微信窗口。
- 会话 ID 固定为 `messaging-home`，历史由 DSH 会话承担；`data/chat-log.json` 只存
  界面要显示的那几轮问答，重启后能恢复。

## 整理链路（DB 版）

```
POST /api/home/organize
  ↓ runtime.dbRecent({sessions:12, perSession:20})      ← 一次 worker 调用，一次 SQL 遍历
  ↓ 组装 bundle（会话名 / 时间 / 方向 / 正文）
  ↓ oneShot(system=整理提示词, prompt=bundle, JSON 输出)
  ↓ {summary, focus[], todos[]}
  ↓ 用户勾选 → POST /api/todos（带 conversationKey，可回溯到人）
```

区别在于：**没有一次微信窗口操作**。旧链路里 `syncCenter({refresh:true})` 是 OCR，
候选名给模型、模型再逐个 `read_messages` 也是 OCR，一次整理要动微信好几回。

## 待办与追踪

待办沿用 `crm` 里的 todos（三态 open/doing/done），整理出来的每条都可以挂到具体会话
（`conversationKey = sha256([provider, username])`），于是：

- 待办页能看到「来自 张三」
- 会话视图能看到这个人身上挂着哪些待办
- 做完点掉，首页计数当场减一

**做完的待办离开「待办」那一组，进「已完成」**：混在"要做/在做"里会让人一眼数不清还剩
几件。表达结果不用文字也不用横线，交付两个东西：

- **不划删除线** —— 横线是"作废"的语义，不是"做完了"。
- **不重复标「已完成」** —— 它既然列在「已完成」下面，状态本来就清楚，再标一遍是冗余。
  只有在别处（会话页）才画状态胶囊。
- 每行右侧一个**删除图标**（原来这里没有任何操作）。
- 来源（自己记的 / 助手记的）只用一个**图标**（人形 / 星），不写文字 —— 这条信息本来
  就不重要，不值得占一行。


## 提醒怎么消掉

自动回复出问题时，首页会有一张「自动回复需要你看一眼」，列出规则名和一句原因。每一行
带一个 **「我知道了」**（`POST /api/automation/ack {ruleId}`）——它把这条规则上未确认的
失败/不确定记录标成已看过，提醒随即消失。自动回复页的「最近处理记录」里也有同一个按钮。

两个刻意的限制：

- **只有"某条记录没确认"的提醒才给按钮**（`projectInbox` 暴露 `acknowledgeable`）。规则
  自己被拦住（`blocked` / `waiting_connection`）是状态问题，标一句"看过了"解决不了，
  给了按钮只会让人点了没反应。
- 按钮旁边必须写明：**看过 ≠ 重试**。发送结果不确定的那条永远不会自动重发。

## 会话视图里放什么

从「最近有动静」点一个人进去，看到的是**聊天记录** + **这个人的待办**，仅此两样。

**打开就停在最新一条**，往上翻才看历史（和聊天软件一致）。实现上是一次读满一窗
（`CHAT_LIMIT = 300`，服务端上限也是 300），拿到正文后把滚动条钉到底；不做分批加载 ——
本地读库本来就便宜，而分批会把滚动位置管理变成一堆状态机（拉取后要保持视野、判到底、
防抖）。窗口用满时在顶部写一句"只显示了最近 300 条"，用户就知道上面不是卡住了。

会话页底部刻意**只做待办**：跟进记录与联系人资料属于 CRM，而产品里暂时没有 CRM ——
摆在那儿只会让"点进来看聊天记录"的人先撞上两块"还没有填写"。真要做 CRM 的时候统一做，
不在会话页里先长一半。空的时候只留一行标题 + 一个「＋ 待办」，不写"没有未完成的待办"
这类空话。

> 实现注意：页头、滚动区、内容块各自是一个**命名变量**再拼起来，不要写深嵌套的 `h()`。
> 曾经因为页头那个 `div` 漏掉一个 `)`，滚动容器被当成页头的子节点 —— 页头 `flex-shrink:0`
> 且高度随内容走，于是整段内容溢出被裁，**页面看着在但滚不动**。`client-smoke.test.mjs`
> 里有一条断言专门盯这个：渲染出来的 HTML 中，滚动区必须出现在页头的闭合标签之后。

## 自动回复模型：官方 + 本地

「设置 → 自动回复模型」列出 **harness 里配置的全部提供方**，不只有官方。本地模型在
harness 里是挂在自己命名空间下的独立 provider（`settings.yaml` 的
`llm-pi-ai.providers.ollama-local`），所以：

- 目录侧 `GET /api/models` 遍历 `ctx.llm.listConfigurableProviders()`，逐个
  `listModels(provider)`，返回 `{provider, providerName, id, name}`。**不在这里维护清单** ——
  用户加一个本地 provider，下拉里自动就有。
- 选中项用 `provider::model` 编码（不同提供方可能有同名模型）；下拉按提供方分 `optgroup`。
- 保存要**同时**写 `auto_provider` 和 `auto_model`（worker 的 `runtime_settings` 表，
  `Harness.run` 把它俩一起放进 job payload）。只换 model 会让请求仍然打到官方端点。
- 生效范围：**后台自动回复的回复生成**。整理、起草、首页对话仍走云端 —— 它们要读懂整段
  上下文，本地小模型容易读偏。界面上把这条写明，不让用户猜。

## 界面文案的底线

**不出现任何"读取本地数据库"的说法。** 实现细节留在源码注释里（开发要看），但界面上只说
用户能感知的事实：「不会打开微信窗口」「不会打扰你」「不会发送任何消息」。`client-render.test.mjs`
里有一条断言专门扫字符串字面量，防止这类话再漏回界面。

## 图标约定

导航五个位置的图标按用户逐条指认定下来（`client-render.test.mjs` 里钉住）：

| 位置 | 图标 | 说明 |
|---|---|---|
| 消息 | 消息气泡 | |
| 待办 | 方框里一个勾 | |
| 自动回复 | 闪电 | 不变 |
| 回复配置 | 圆盘 + 辐条 | 就是原来那颗「设置」图标 |
| 设置 | 通用齿轮 | 外齿 + 内圆 |

**纯图标按钮必须留点击留白。** 待办来源（人形 / 星）与删除（垃圾桶）都是 16px，
外面套 `iconButton`（6px 内边距 ≈ 28px 点击区），颜色与 hover 交给 `.ma-iconbtn`
（行内样式会盖掉 CSS，所以颜色不能写在 style 里）。原来的 13px 图标用户
「看不清、操作不方便」。来源与删除都只给 `title` + `aria-label`，不写可见文字。

**第二行必须是「左信息 / 右操作」两栏。** 已完成条目里，删除入口固定在第二行右侧
（`justifyContent:'space-between'` + 按钮 `flexShrink:0`），标题多长、文案几行都挤不掉它。
行标题要带 `minWidth:0` + `wordBreak:'break-word'`，否则一条超长连续串会把右侧顶出这一行。

## 「已完成」里每一行都能删

已完成里有三类行，**每类都必须有删除入口**（用户报过"这 2 条没有显示删除图标"）：

| 行 | 删的是什么 |
|---|---|
| 做完的待办（`todo:<id>`） | 真删：`POST /api/todos/<id>/delete` |
| 助手处理过的消息（`job:<id>`） | 从清单移除：`POST /api/receipts/dismiss` |
| 你标成已看的会话（`done:<key>`） | 从清单移除：同上 |

后两类是**处理回执**，记录的是客观发生过的事，删不掉也不该删 —— 所以 dismiss 只往
`data/dismissed.json` 记一个 id，`projectToday` 按它过滤，不碰任何事实数据。

## 原生对话框入口

`回到对话框` 从导航底部的常用项降级为**只在开发者模式出现**的小入口，而且开发者模式
**默认关闭**（原来默认打开，是因为产品还在搭、处理引擎就是原生的）。理由：产品自己
已经能聊天、能整理、能看消息，原生界面（工作区、模型选择器、工具 JSON）是开发面。

按 **Esc 只往回退一步**，绝不离开产品：开着会话就先退回列表，再按一次收起面板（停在封面）。
原来 Esc 直接 `cover:false`，而那就是把画面交回 DSH 原生界面 —— 按一下掉进开发界面，
用户会以为产品崩了。

## 边界（明确不做）

- 不做后台监听：整理只在用户点击时读一次 DB。
- 不发消息：整理与对话都不触达发送链路；发送仍然只走自动回复 / 人工确认的草稿。
- 不引入向量检索：会话量小，直接截断注入即可（见 `retriever.mjs` 的架构决策）。
