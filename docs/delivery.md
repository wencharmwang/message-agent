# 交付说明：两种方式

**一句话**：两种交付方式产出的东西**完全一样** —— 都只是一个符合
`docs/unlocked-db-protocol.md` 的「已解锁数据库目录」。

所以：客户可以先自助、跑不通再找你；也可以随时从一种切到另一种，
**项目侧一行都不用改**。这是当初把解密解耦出去换来的好处。

---

## 一、对比

| | **方式 A：你提供解锁** | **方式 B：客户自己用 Agent 解锁** |
| --- | --- | --- |
| 面向 | 不折腾、要开箱可用、愿意为省事付费 | 能自己动手的客户 / 开发者 |
| 客户拿到 | 两个公开仓库 + **已解锁目录**（或私库授权） | 两个公开仓库 + 协议文档 + **提示词** |
| 客户要做的 | 填一次配置 | 用提示词让 Agent 产出目录，再填配置 |
| 你提供的 | 解锁能力（工具授权 或 代操作服务） | 只有**接口约定** + 指向公开第三方 |
| 谁来操作 | 你（或你的工具在客户机器上） | 客户的 Agent |
| 出错时 | 你兜 | 客户按提示词自救，兜不住再找你 |

---

## 二、方式 A：你提供解锁

两种落地形态：

**A1 —— 客户机器上，客户跑你的私有工具**（`wechat-db-lab`，只发给授权客户）
- 客户执行解锁 → 得到产物目录 → 填进 `unlocked_root`
- 好处：**数据不出机器**，你也不接触客户的聊天内容

**A2 —— 你远程/上门协助**
- 适合完全没有动手能力的客户。你操作，客户看着
- 同样用私有工具，只是由你执行

> ⚠️ **不要**把"已解密的数据库"打包发给客户。
> 那是客户的聊天记录，每天都在变（时效性差），而且一旦经过你手里再外流，
> 就是一次数据事故。**让解密发生在客户自己的机器上。**

---

## 三、方式 B：客户自己用 Agent 解锁

客户拿到的三样：

| 给什么 | 文件 |
| --- | --- |
| 项目本体 | `message-agent` + `messaging-runtime`（公开，MIT） |
| 产物协议 | `docs/unlocked-db-protocol.md` |
| **提示词** | `docs/self-unlock-prompt.md`（两段：① 准备数据 ② 排障） |

客户流程：

```
装好项目 → 把提示词①发给自己的 Agent → 拿到产物目录
        → 把路径填进 config.json 的 unlocked_root → 跑 restart.ps1
```

提示词里刻意只写**要求**（产物必须长什么样、必须合并 WAL、只读、只处理自己的数据），
并指向公开第三方项目作参考 —— **不写具体做法**。

---

## 四、两种方式共同的验收标准（可脚本化）

1. **自检**：`UnlockedSource(<产物目录>).ready()` 返回 `True`
   （客户自检与程序启动用的是**同一段代码**，不会有"自检过了程序还挑毛病"）
2. **三个端口都在听**：`8766` 消息运行时 / `3080` 引擎 / `8767` worker
3. `GET /api/unlocked` → `ok: true`，`databaseCount ≥ 5`
4. `GET /api/conversations` → 能列出真实会话
5. **端到端**：在界面上发一条测试消息，能正常回复

---

## 五、客户侧怎么启动 / 怎么停

| 场景 | 命令 |
| --- | --- |
| 源码检出（首次） | `python prepare.py` → 改 `config.json` 的 `unlocked_root` → `.\restart.ps1` |
| 打包安装 | `packaging\install.ps1` → 改配置 → `restart.ps1` |
| 只是重启 | `.\restart.ps1` |
| 先看会停什么 | `packaging\stop.ps1 -DryRun` |
| 真停 | `packaging\stop.ps1` |

> **必须在客户自己的终端里跑 `restart.ps1`。**
> 用别的工具/会话把它拉起来，进程会随那个会话结束被回收 ——
> 表现成"起来了但过一会儿就没了"。（这个坑我实测踩过。）

---

## 六、平台与前置条件

| 项 | 说明 |
| --- | --- |
| **操作系统** | **仅 Windows**。取密钥这一步依赖读进程内存，macOS 上被 SIP 拦住（`task_for_pid` 被拒），不通 |
| 微信客户端 | 需要在本机登录过（数据在本地） |
| 运行时 | 打包版自带 Node + Python，客户不需要自己装 |

---

## 七、数据会过期 —— 这是常态，不是故障

- 产物是**某一时刻的快照**。微信每天新增消息，产物自然"落后"。
  **重新解锁一次就行**（方式 A 找你 / 方式 B 再跑一遍提示词）。
- **密钥本身很稳**：同一账号的密钥**不会因为微信升级而失效**；
  只有换账号 / 重新登录 / 数据被重建时才需要重新获取。
- 判断产物新旧：看 `manifest.json` 的 `created_at`，以及各库 `source` 的 mtime。

---

## 八、责任边界（实际落成了什么样）

- **方式 B 的公开仓库里只有**：产物协议（产物长什么样）、指向公开第三方项目、提示词。
  **不含任何做法** —— 不含取密钥、页解密、偏移、参数。这是刻意的。
- **方式 A 里由你（或你的私有工具）实际执行解锁**，所以解锁能力只出现在
  你发给授权客户的私有库里，**不进公开仓库、不进安装包**
  （安装包已经不再打包任何解密组件，有测试钉住这一点）。
- 两种方式都只应处理**客户自己的数据**（他自己的机器、他自己的账号）。

> 一句实话：方式 B 把"要不要提供手段"这个问题**推给了客户和第三方项目**，
> 这让你的公开仓库保持干净；但它换不走全部风险 —— 公开分发的范围仍然是你的事。

---

## 九、三个仓库各自是什么（交付产物清单）

| 仓库 | 可见性 | 里面是什么 | 谁拿到 |
| --- | --- | --- | --- |
| **`message-agent`** | **公开（MIT）** | 产品本体：界面与插件（`plugin/`）、worker（`agent_worker/`，含**只读**的 `wechat_reader/`）、Agent 预设（`presets/`）、启动与安装脚本（`launch.py` / `restart.ps1` / `packaging/`）、协议与交付文档 | 所有客户 |
| **`messaging-runtime`** | **公开（MIT）** | 消息运行时：发送用的本机驱动（个人微信没有官方 API，靠操作本机微信）、自带的 Python/Node 运行时、语音解码组件 | 所有客户 |
| **`wechat-db-lab`** | **私有** | 解锁工具：取密钥、页解密、合并 WAL、写 manifest；另含它自己的网页与 macOS 相关调研文档 | **只给授权客户**（或由你执行） |

### 两种方式各发什么

| | `message-agent` | `messaging-runtime` | `wechat-db-lab` | 客户另外需要 |
| --- | --- | --- | --- | --- |
| **方式 A：你提供解锁** | ✓ | ✓ | ✓（授权给客户）或由你远程执行 | 无，装完即可用 |
| **方式 B：客户自己解锁** | ✓ | ✓ | **不发** | 一份自备的「已解锁目录」 |

### 打包后的产物（最终用户拿到的形态）

| 产物 | 由谁产出 | 内容 |
| --- | --- | --- |
| `MessageAgent-<版本>-win64.zip` | `packaging/build-package.ps1` | 产品本体 + **自带 Node/Python**（客户不用自己装）+ 引擎归档 + 安装脚本 + `manifest.json`（逐文件 sha256 清单） |
| 消息运行时安装包 | `messaging-runtime` 自己的发布流程（本仓库不带打包脚本） | 运行时本体 + 自带解释器 + 语音解码器 |
| **「已解锁目录」** | **客户机器上现场产生** | `manifest.json` + `plain/` 下的明文库。**绝不随包分发** —— 那是客户的聊天记录，每天都在变，经手即风险 |

> 安装包里**只有**产品本体与运行时。**不含任何解密组件** ——
> 这条有自动化测试钉住（`agent_worker/test_isolation_boundary.py`）：
> 安装脚本里一旦出现解密相关的引用，测试就失败。

### 三个仓库的依赖方向

```
message-agent（公开）  ──需要──▶  一个「已解锁目录」（外部产出，不是仓库）
        │
        └──启动时──▶ messaging-runtime（公开，负责发送）
        
wechat-db-lab（私有）──产出──▶  那个「已解锁目录」
```

**关键**：`message-agent` **不依赖** `wechat-db-lab` —— 它连 import 都没有
（有测试钉住）。所以方式 A 和方式 B 对产品侧完全相同。
