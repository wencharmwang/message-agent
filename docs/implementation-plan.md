# Message Agent 分步实施计划

日期：2026-09-09。本轮完成设计；下面所有实现步骤均未执行。优先级遵循“先界面改造，再进入打包实现”。

## 阶段 0：架构基线（本轮）

已完成：核验三个项目和引用讨论；确定 [界面与业务架构](architecture.md)、[单产品交付方案](packaging.md)。未修改运行代码、配置、数据库或计划任务。

## 阶段 1：可运行的消息工作台

### 1.1 插件结构与界面骨架

修改 `plugin/package.json`、拆分 `plugin/client.js`，新增客户端构建配置与产品 profile。实现消息/自动化/设置导航、联系人列表与原生会话承载，保留现有消息助手设置可回退入口。复用 Harness slot、主题和会话状态；先用明确标识的测试 fixture 做开发验证，生产默认真实空状态。

验收：真实 profile 启动并载入插件；页面切换、选中态、窄窗口、键盘操作和中文长文本可用；原生流式回复和会话恢复不回归；插件卸载无重复注册/计时器。此步同时验证页面 slot 是否足够，必要的小型引擎扩展记录在补丁清单。

普通用户验收补充：主路径不得出现 Agent、Session、MCP、workspace、preset 等开发者概念；用户无需阅读说明即可找到消息、与助手对话、开启/关闭/编辑/删除自动回复。模型、引擎和诊断信息只在高级设置中展示。

### 1.2 业务工具呈现

新增消息工具卡片和纯映射函数，接入 `tool.call.toolview`。从真实工具 wire name、参数及结果读取身份、数量、覆盖范围与错误。把 `submit_reply_decision` 显示成拟稿/跳过/需用户处理；保留状态详情入口。

验收：运行中、成功、失败、取消、未知工具及历史回放均有正确文案；工具执行成功不误报已发送；使用无密钥记录回放和组件测试，不向真实微信发送测试内容。

### 1.3 Inbox 真实数据与会话关联

在 `plugin/host` 新增 Inbox 聚合，扩展 Worker 的必要只读查询。复用 `reply_rules`、`reply_jobs` 与 `conversation-sessions.json`；区分自动会话和交互会话绑定。迁移规则管理组件为自动化页面，修正文案和状态标签。

验收：联系人改名不丢历史，同名联系人不串会话；同一联系人重启后仍关联原任务；新建交互不会执行自动回复流程；无规则、无消息、离线、waiting_visible、needs_user、failed、blocked 均可识别；刷新列表不触发隐式历史同步；分页没有重复遗漏。

### 1.4 草稿和发送确认

新增持久化人工草稿、版本比较和确认/修改/取消 API。先实现展示，再经 RuntimeAdapter 接通受信任审批与相同请求的后续发送。验证现有 CLI 管理接口是否可复用；不足时仅向 Runtime 添加独立管理能力，不把批准能力暴露成普通 MCP 工具。

新增联系人级人工/自动任务协调，明确会话变化、版本冲突、双击、过期、规则暂停、服务退出的行为。保持现有自动规则授权，不强制给每条自动回复再加人工确认。

验收：同一确认只产生一个发送请求；修改后旧批准不可发送；取消后旧 pending 不再执行；发送中/uncertain 不允许自动重发；刷新、断连与重启能查询实际状态；凭据不进入客户端包；未经认证的确认被拒绝；现有自动回复、规则停用、去重和恢复测试通过。使用模拟 Provider 验证完整链路。

阶段 1 完成定义：用户能从真实消息列表进入上下文、与助手交互、理解动作、审阅并操作回复草稿、查看真实发送结果、管理自动化；默认不暴露开发者概念。仅完成导航或静态卡片不算完成。

## 阶段 2：待办与客户（界面主体完成后）

先提供待处理事项投影，再新增可完成/延期的业务 Todo 与来源证据；之后实现客户资料、AI 摘要、阶段和跟进。外部 CRM 先保留业务适配边界，不实现没有当前消费者的复杂框架。

验收：资料与待办可持久化、可追溯来源、可由用户修正；模型推断不会覆盖已确认资料；能从客户返回消息并携带上下文询问助手；不把全部微信联系人自动当作客户。完成此阶段再展示最终“消息/客户/待办/自动化”导航。

## 阶段 3：内置依赖与打包基础

在阶段 1 界面验收后开始：固定并内置 Harness、替换源码 import、实现路径解析、生产 profile 与 staging 构建；先做可独立运行目录，后做安装器。阶段 2 的业务扩展可独立排期，不阻塞这项基础交付工作。

验收：隔离目录完全脱离外部 Harness 源码启动；已构建插件正常加载；所有路径来自配置解析；单一产品目录包含运行依赖，用户数据位于可写 dataRoot；Runtime external/managed 模式正确。

## 阶段 4：正式分发

补充安装、升级、卸载、版本清单、数据迁移和回退验证；桌面外壳单独决策。按照打包设计中的发布门槛，在无开发环境的 Windows 环境做发行物验证。

## 每一步的交付约定

每步提交可独立检查的代码和对应说明，运行该步相关检查，不以全量 Harness 测试代替业务验证。涉及 Harness 修改时遵守其 AGENTS：真实 profile 装配、用户可见变化的记录回放、locale、Agent Note 和相关检查。纯文档阶段只验证来源与文档链接，不运行会影响正在工作的消息服务的安装/烟测脚本。

回退优先切回上一产品 profile/插件版本，保留原数据与状态。数据库新增要有显式迁移和版本检查；不得删除发送记录来解锁流程。每步完成时报告实现项、验证结果和仍未实现项，不把设计计划描述为已上线能力。
