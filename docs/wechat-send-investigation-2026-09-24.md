# 微信输入/发送排查（2026-09-24）

## 实机证据

- 本机微信 4.1.15.13；可执行文件修改时间 2026-09-23。窗口包含 `MMUIRenderSubWindowHW`，旧输入实现仍假设顶层窗口把 WM_CHAR 路由给 Qt 编辑器。后台输入兼容性可疑，但未对新旧微信版本做 A/B，不能断定升级是唯一根因。
- 最近两次发送的持久化回执为 `not_sent / not_submitted:send_failed`；此前另有 `contact_not_found`。旧驱动把具体异常统一压成 send_failed，上层又忽略 receipt.verification，导致界面“原因未知（没有错误码）”。这些历史回执无法还原具体输入失败原因。
- 文件传输助手前台输入成功，绿色发送按钮出现；测试草稿已撤销，没有发送消息。
- 实机只读探测：999×810、DPI 96，输入区域 (505,666,472,86)，完整布局可识别。旧/新按钮区域在本次测试均能检测绿色，旧区域仅覆盖按钮上部；不能把按钮偏移认定为本次唯一根因。
- “空输入框必须有明显颜色变化”的就绪判断存在确定性缺陷：纯色空框会被判未绘制。新增浅色/深色回归用例。本次带光标/占位文字的实机旧判断通过，因此不宣称它解释所有历史失败。

## 已部署调整

- 当前 Runtime 配置改为 foreground：激活微信、确认窗口与坐标、粘贴一次，然后点击识别到的发送按钮，不依赖 Enter 发送偏好。
- 就绪检查改为完整布局识别；扩大右下角按钮检测范围覆盖新旧位置。
- 去掉无条件重写文字，改为只等待绘制；检测到已有可发送草稿时拒绝覆盖。
- 保留驱动错误码，经 receipt.verification 传给手动发送与自动回复记录。
- 只有明确 sent 才展示成功；不确定结果保留拟稿并提醒核对。
- 停止部署过程中发现的七个历史 Runtime 监督进程残留，恢复正式计划任务。

## 验证边界

69 项驱动测试（包括需显式开启的实机探测入口）、7 项 Worker 测试、38 项界面测试通过。实机探测单独开启验证过完整布局和有文字时的按钮识别。服务恢复，诊断确认 foreground_guarded_input，Worker 状态接口返回 200。

尚未向联系人执行真实发送，端到端投递成功仍需下一次用户授权发送确认。历史失败消息没有重放。前台发送会短暂切换到微信。
