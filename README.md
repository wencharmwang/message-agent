# Message Agent

上层消息 Agent，复用用户已有的 DeepSeek Harness 原生 Web UI、工作区、会话、模型路由和工具执行。

## 分层

- `deepseek-harness`：原生聊天界面及 Agent 运行时；普通任务使用完整的 `message-agent` 预设。
- 本项目：用户主动发起的消息整理、联系人/群组自动回复规则、事件去重、任务状态和原生设置插件。
- `messaging-runtime`：消息 MCP、微信驱动、后台读写、发送授权及幂等回执。上层不直接操作微信窗口。

部署目录为 `C:\Users\<你>\Documents\projects\message-agent`，入口是 `http://127.0.0.1:3080/`。首次打开使用 Harness 启动时生成的本地认证链接；后续浏览器保留登录状态。

在原生界面「设置 → 消息助手」读取会话、选择联系人或群组、设置提示词并启用。启用时先记录当前消息作为基线，只响应之后的新消息。Wencharm 的原有暂停状态已迁移保留。

产品界面聚焦一条核心路径：**自动回复**。只有用户明确启用的联系人或群组会进入轮询；它使用下述基线、去重、发送前复读和幂等保护。添加规则后默认保持暂停，用户检查回复要求后再手动开启。

首屏是「消息」：**关键信息 + 关键操作 + 对话**。关键信息（等你回复的人、待办、今天的新消息、自动回复异常）全部由本地解密数据库与本地 job 状态确定性算出来，不调模型、不碰微信窗口；关键操作只有一条 —— 「整理消息」读最近几个会话的正文，交给模型归纳出「发生了什么 / 谁需要你回应 / 有哪些事要做」，结果留在页面上，待办由用户勾选后才入库。右下角的对话区是一个模型会话，每次提问都由上层把一份本地数据库快照拼进提示词，所以它回答的是真实消息，而不是去开微信窗口读。导航第二项「待办」承载后续追踪：做完的待办离开「待办」进「已完成」，用状态标签表达，不画删除线。

自动回复出问题时，首页会列出来并带一个「我知道了」按钮（`POST /api/automation/ack`，自动回复页的处理记录里也有），点过之后这条提醒不再出现。它只是"看过了"，绝不代表重试 —— 发送结果不确定的那条永远不会自动重发。规则自己被拦住（读不到微信、等待连接）时不给这个按钮：标一句"看过了"解决不了状态问题，给了按钮只会让人点了没反应。

界面文案不出现任何实现细节（例如"读取本地数据库"）：只说用户能感知的事实 —— 不打开微信窗口、不打扰你、不会发送任何消息。

主动查消息不再需要回到原生对话框。原生界面（工作区、模型选择器、工具 JSON）是开发面，「回到对话框」只在开发者模式打开时出现在导航底部。旧版基于 OCR 的「消息整理」页（先刷新可见列表拿候选名、再按名字逐个打开会话去读）已整体撤除：那一步会抢走用户正在看的会话、清掉未读红点，而且只覆盖滚在顶上的十来行。历史 message-center 接口暂时保留用于兼容已有本地数据，但不进入首版产品导航。

自动任务使用 `message-auto` 预设，具备消息工具调用能力，以只读、无需交互的权限运行。需要更多权限或人工决定时停止该任务。模型产出的回复经上层校验、规则复核、会话复读后进入持久化发件箱，再由 Runtime 验证该请求的联系人、正文、规则版本和有效期。交互任务同样只呈现消息处理能力；通用开发工具不出现在面向普通用户的产品界面中。

日常聊天优先自然接续；未知的生活状态不会被编造成事实，也不会一律转人工。真正需要本人承诺或授权的消息才标记为待人工处理，后续新消息仍继续监听。自动任务通过 `submit_reply_decision` 工具提交正文和独立的内部理由，不再解析最终聊天文本中的 JSON；工具提交不等于已经发送。自动任务默认使用 low 推理和 4096 输出 token，普通交互任务保持原有模型设置。

同一 provider 和 conversation ID 的新消息会接续同一个原生 Harness 会话，标题直接使用联系人或群组名称。联系人改名不新建会话；不同联系人、群组或账号入口分别保存。收到的新消息作为用户输入推进 Harness 会话活动时间，使该会话回到最近列表。绑定写入 `data/conversation-sessions.json`，服务重启后通过 Harness 的 resume API 恢复原会话及历史。每条消息仍有独立 job/request ID，保证发送去重；本轮提交工具随任务注册和释放，不复用上一轮的决定。同一会话已有任务运行时拒绝重复调度。

会话历史中的拟稿不视为已发送；每次任务附带近期发件状态和当前微信消息快照。面板显示「回复已拟好」表示模型已完成拟稿，最终是否发送以消息助手中的任务状态为准，不需要另一次人工复核。

模型或 Harness 在生成阶段失败时，该条任务记为 `failed`，联系人保持监听，下一条消息仍会处理。只有已经进入发送阶段且结果无法确认时才使用 `blocked`，避免可能重复发送。恢复旧会话时每轮都会重新施加自动回复的输出 token 上限，防止提供方默认值覆盖本地配置。

新消息触发只比较微信左侧聊天列表中的最新摘要和显示时间，不再用整段 OCR 历史对齐判断是否有新消息。列表发生稳定变化后才进入对应聊天，读取最后一条真实气泡；最后一条为收到的文本时交给 Agent，最后一条为我方消息或非文本时只更新状态。`blocked` 保留给发送结果不确定等可能导致重复发送的状态。

## 启动与维护

Windows 登录任务 `Messaging Agent` 托管 `launch.py`，共同管理 Harness Web 和消息 worker；停止任务会关闭整个进程树。`Messaging Runtime` 仍独立运行。旧 `Messaging Auto Reply` 任务已停用。

- `config.json`：模型、轮询间隔、超时、运行时和 Harness 路径。
- `data/reply.db`：规则与自动回复任务。`data/*.token` 是本地授权凭据，不应分享。
- `.harness/`：原生 Harness 配置和可恢复的会话历史。
- `workspace/`：消息任务工作区；普通任务也可在原生界面选择其他工作区。
- `plugin/`：原生设置页插件和新消息到 Harness Session 的适配器。
- `presets/`：基于 Harness standard 预设生成的完整 Agent 组合；没有修改 Harness 的 Agent 循环。

配置修改后重启 `Messaging Agent`。更新代码可运行 `install.ps1`。首次由旧版本升级，停止旧 worker 后运行 `migrate-state.py`，再部署 Runtime 对应的外部数据库路径。旧数据库保留用于回退，不会覆盖新库。

## 读取与验证边界

**读走本地数据库，发走 UI。** 首页、整理、会话正文、说话方式分析全部读一份**外部准备好的「已解锁数据库目录」**（`plain/session/session.db`、`plain/message/message_N.db`，`mode=ro&immutable=1`），一次读库只遍历一遍分片。**本项目不解锁** —— 它不取密钥、不做页解密、不读进程内存，只按协议读别人产出的明文副本（协议见 [`docs/unlocked-db-protocol.md`](docs/unlocked-db-protocol.md)）。它不打开微信窗口、不抢前台、不清未读红点，也不受"左侧列表只能看到十来行"的限制。发送仍然走 messaging-runtime 的后台点击（个人微信没有官方 API），所以发送会短暂把微信切到前台。

代价是数据源依赖那份产物：没配 `unlocked_root`、或产物不合格时，整条读取链路为空（此时首页会直说"还没有读到会话"），而不会退化成读错内容。产物缺什么、为什么不合格，启动时的校验会逐条说清。

验证包括后台微信只读探测、原生 Harness 真实模型任务、模拟消息端到端测试（回复、暂停、去重）、同一会话多轮续聊及重启恢复、联系人隔离，以及上层和 Runtime/WeChat 回归测试。界面另有两层自动化体检：`plugin/client-render.test.mjs` 钉住界面约定（导航结构、"回到对话框"只在开发者模式出现、OCR 版整理页不得复活），`plugin/client-smoke.test.mjs` 用 react-dom/server 把每个页面真的渲染一遍，抓"白屏"这类只有打开页面才会发现的错误。会话复用测试使用模拟消息，不向真实联系人发送测试消息。
